# Configure a new application

1. Create a separate Amplify application/environment. Do not connect the starter to the source application's outputs, buckets or tables. Configure the backend values listed below in the deployment environment; the required business ID must also be available there.
2. Provide existing image and platform-status buckets in the deployment region, matching the original bucket architecture. Configure image upload CORS/read access for the new site's needs. The image handler returns direct S3 URLs. The platform-status object is `status.json`; set the public status URL accordingly.
3. Configure Cognito and provision initial users using the original roles: `Bytewave-Admin`, `Admin`, `Support`, `Client`. Preserve tenant/business assignments and the existing authorization model. Set `VITE_APP_USER_POOL` for the original administrative service calls even when generated outputs configure sign-in.
4. Configure SES identities and sending permissions in the application's region. Set the support and billing sender addresses and billing/hosting recipients. Use matching public contact addresses. Validate SES delivery and any sandbox restrictions before launch.
5. Store `TURNSTILE_SECRET_KEY` and `STRIPE_SECRET_KEY` through Amplify secrets. Set the matching public Turnstile site key and Stripe publishable key. Never expose secret keys through Vite variables.
6. Create/associate a Stripe EventBridge destination for the new application. Set `STRIPE_EVENT_BUS_ARN` and `STRIPE_EVENT_MODE` (`test` or `live`). Production requires live mode. Without the ARN, the existing backend omits Stripe event wiring and warns; do not accept payments until it is configured. Retain the source integration's event types and metadata contracts. No HTTP webhook signing secret is used by this starter.
7. Set the HTTPS `PAYMENT_SITE_ORIGIN` without a trailing slash, plus additional origins in comma-separated `CORS_ALLOWED_ORIGINS`. Configure the corresponding frontend origin and business ID. Provision the new business/content records through the existing workflows; no records are copied.
8. Generate the new application's Amplify outputs and rebuild. Run a test-environment walkthrough of sign-in/password changes, role access, public data/retry, contact delivery, uploads, admin editing, ticket notifications and Stripe payment/subscription/billing notifications before production.

The original monitoring definitions remain disabled in `amplify/backend.ts`. No infrastructure has been deployed as part of extracting this starter. Backend type checking is not a CloudFormation synthesis or live integration check.

## Local settings versus deployment setup

`.env.example` contains the everyday frontend settings used by the source application. `VITE_APP_GOOGLE_ANALYTICS_ID` retains the source analytics integration; configure it for the new client.

Generated `amplify_outputs.json` normally supplies Cognito configuration and the API endpoint. `VITE_APP_API_GATEWAY` is a fallback. The existing administrative service separately reads `VITE_APP_USER_POOL`; set it to the new pool ID when using that workflow. `VITE_APP_USER_POOL_CLIENT_ID` is only needed alongside that pool ID if configuring sign-in without generated outputs.

The extraction introduced these public identity overrides to replace hardcoded Bytewave branding. Set them in the frontend build environment (or `.env.local` during development) when configuring the client:

| Setting | Purpose / default |
| --- | --- |
| `VITE_APP_NAME` | Display name; defaults to `Website` |
| `VITE_APP_SITE_ORIGIN` | Canonical/email link origin; defaults to the browser origin |
| `VITE_APP_SUPPORT_EMAIL` | Support address used by ticket notification requests; configure before using ticketing |
| `VITE_APP_BILLING_EMAIL` | Billing contact displayed on invoices; configure before using billing |

## Backend deployment values

These belong in the Amplify deployment environment, not the local frontend example. A Vite `.env.local` file does not by itself supply backend synthesis variables. Some values below replace constants from the original application; they are not automatically generated by this starter.

| Setting | Purpose |
| --- | --- |
| `APPLICATION_NAME` | New application's API naming prefix |
| `BUSINESS_NAME` | Business display name in notification emails |
| `VITE_APP_BUSINESS_ID` | New business ID, also required during backend synthesis |
| `PAYMENT_SITE_ORIGIN` | HTTPS site origin without a trailing slash |
| `IMAGES_BUCKET_NAME` | Existing bucket selected for this application's images |
| `PLATFORM_STATUS_BUCKET_NAME` | Existing bucket selected for platform status |
| `SUPPORT_EMAIL` | Support notification sender/recipient |
| `BILLING_EMAIL_FROM` | Verified billing sender |
| `BILLING_NOTIFICATION_EMAIL` | Billing notification recipient |
| `HOSTING_NOTIFICATION_EMAIL` | Hosting notification recipient |

Additional settings as needed:

- `CORS_ALLOWED_ORIGINS`: comma-separated origins beyond the payment site origin, such as `http://localhost:5173` for local development.
- `STRIPE_EVENT_BUS_ARN` and `STRIPE_EVENT_MODE`: select the new Stripe partner bus and `test`/`live` mode before accepting payments.
- `STRIPE_AUTOMATIC_TAX`: defaults to `false`.
- `DEPLOYMENT_ENV`: optional fallback when `AWS_BRANCH` is unavailable; otherwise defaults to `sandbox`. Amplify Hosting supplies `AWS_BRANCH`.

Store `STRIPE_SECRET_KEY` and `TURNSTILE_SECRET_KEY` through Amplify secrets as part of integration setup. They do not belong in the public frontend example.

The original robots exclusions and public `status.json` are retained. Publish a sitemap for the new domain and add its URL to `public/robots.txt`; the original domain-specific sitemap is intentionally excluded.
